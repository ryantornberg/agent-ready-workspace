## Slice 0, the eval harness re-recorded

Built on the branch `m2/slice-0`, in a separate working copy outside the repository folder, at the driver tier, under [changing the machinery](../changing-the-machinery.md).

**What was built.** Each change has a test in `tests/test_core.py` (`EvalHarnessApartTests`). Seven of its eight tests failed at the base commit, `397e972`, and all eight pass at the tip. The eighth holds the harness's file listing and hash to the check's; it passed at the base too, and guards the new listing.

- `grade.py` loads the graded hook's own file, so `wslib/parts.py` left the eval hash. Only the hook's own file and the harness count. Neither `run.py` nor `grade.py` imports anything from `wslib/`. In a scratch copy, an added hook event and an edited snapshot module leave every record as it was (criterion 2).
- `leaks()` reads each transcript string instead of the JSON text, so a Windows path written with backslashes is found. The test runs on all three systems, and the Windows skip in the older temporary-folder test is gone (criterion 27).
- `eval_record` needs 40 or more runs in every arm, pooled across the cases (criterion 1). Its cases now hold 40-run records, and a new case shows 5 runs per arm failing.
- Git ignores `.claude/worktrees/` (criterion 28).
- `AGENTS.md` and `INDEX.md` were not edited. Nothing slice 0 changes is named there; what slices 1 to 5 add waits for slice 6's recording.

**How the work was saved before the paid runs.** The harness commit used `--no-verify`, as the machinery page's trap says and as the approval made standing. `check --staged` showed only the three `eval_record` findings, and the message check was run by hand.

**Results.** Recorded on `claude-haiku-5-5` with Claude Code 2.1.326, fifteen runs per arm in each case. Runs passing every grader, with the 95% Wilson interval:

| Case | Guided | Two-line | Bare |
|---|---|---|---|
| big-report | 15 of 15: 100% (80% to 100%) | 4 of 15: 27% (11% to 52%) | 0 of 15: 0% (0% to 20%) |
| fix-a-bug | 15 of 15: 100% (80% to 100%) | 15 of 15: 100% (80% to 100%) | 0 of 15: 0% (0% to 20%) |
| nightly-job | 15 of 15: 100% (80% to 100%) | 0 of 15: 0% (0% to 20%) | 0 of 15: 0% (0% to 20%) |
| **Pooled** | **45 of 45: 100% (92% to 100%)** | **19 of 45: 42% (29% to 57%)** | **0 of 45: 0% (0% to 8%)** |

Guided against two-line, one-sided Fisher exact test: p = 8.4e-11. Guided against bare: p = 9.6e-27. The eval did not lose. Every comparison M1's recording won still holds: guided beats bare in each case, and guided beats two-line in nightly-job, in big-report and pooled. [evals/README.md](../../evals/README.md#the-recorded-runs) has the per-grader table.

**Agent runs: 139 of the 150 allowed.** One probe run, which held on all nine points; three smoke runs, one per case on three different arms; and 135 recorded runs. No run failed to start, so none was repeated.

**Before the commit,** the transcripts passed the deny list through `check`, and the harness's own `leaks()` found nothing in any of the 135.

**Run live in the main checkout after the merge,** at `5baa8a8`: `selftest`, `check`, `check --phase ci` and the unit tests pass; `grade.py --recorded` finds no difference; importing `grade.py` loads nothing from `wslib/`; git ignores `.claude/worktrees/`; `leaks()` finds nothing in the 135 stored transcripts.

## Slice 1, direct-push and admin-merge refusals

Built on the branch `m2/slice-1`, in a separate working copy outside the repository folder, at the driver tier, from the walled reader's two descriptions.

**What was built.** Fourteen new tests failed at the base commit, `eb567e5`, and pass at the tip: `DirectPushTests` (12), `AdminMergeTests` (1) and `test_cases_bite` (1, one subtest per new part).

- `direct_push`, a check in a new `push` phase, run by a new pre-push hook through `ws.py check --push`. A push to main that adds a commit changing a machinery path is refused, naming the commit, its subject and the path (criterion 3). A doc-only push, a push to another branch and a deletion pass (criterion 4). A merge is judged by the commits it brings in. The part and its list come from the remote's current tip, so a push that drops paths from the list is judged by the old list. A range that cannot be listed, or a remote tip with no readable manifest, refuses a push to main. A test pushes through `git push` itself, with two refspec forms.
- `no_admin_merge`, a before-shell hook that refuses `gh pr merge --admin` in every form the cases name, and allows a merge without it and a quoted mention (criterion 33). It loads its command-line parser from `no_stage_all`'s file instead of editing that file, which the eval hash covers.
- The machinery list lives once, in the `direct_push` entry of `workspace.json`; a test fails when the machinery page's table differs (criterion 34).
- Both new parts' messages name `docs/changing-the-machinery.md` (criterion 32), and a do-nothing stub fails at least one case of each (criterion 22).

**Decided while building.** The agent settings file counts as machinery as a whole. The source counted it only when its hook entries changed; slice 2 will change it for the browser setting, and that change belongs on a branch anyway. A new main is checked over its whole history, so a new repository's first push needs `--no-verify`; the machinery page says so.

**Agent runs:** none.

## Slice 2, one browser per session

Built on the branch `m2/slice-2`, in a separate working copy outside the repository folder, at the driver tier, from the walled reader's description.

**What was built.** Four new tests failed at the base commit, `009f26b`, and pass at the tip: three in `BrowserIsolationTests` and the new part's subtest in `test_cases_bite`. The opt-in `tests/test_browser.py` could not run at the base, which had no `.mcp.json`.

- `.mcp.json` and `.codex/config.toml` run `@playwright/mcp@0.0.84`, the newest release at least two weeks old, with `--isolated`. `.claude/settings.json` turns the browser plugin off by name. Both new files joined the machinery list and the machinery page.
- `browser_isolation` fails when the plugin is not set to `false`, when a config's server lacks `--isolated` or an exact version, or when a config is missing or unreadable, for each tool's config (criterion 5). Codex's TOML is read line by line, since Python 3.9 has no parser for it.
- `docs/browsers.md`: the Windows form, Chrome, local settings that can undo the project's, the two tool-name prefixes, and that an isolated browser forgets logins.

**Results.**

- The opt-in test, on macOS with Node 26 and Chrome: two isolated servers both opened `about:blank` (criterion 6). Two servers sharing one profile folder collided, and the second reported "Browser is already in use for ..., use --isolated to run multiple instances of the same browser" (criterion 7).
- One recorded Claude Code 2.1.326 session in the working copy listed the project's `playwright` server as connected, with 25 browser tools and none of the plugin's (criterion 35). A replay test holds the record to the committed config.
- One Codex CLI run in the working copy, trusted for that run only, finished, but its output does not say whether it started the project's browser server, and `codex mcp list` lists only user-level servers. So Codex is held to the config rule by the check, and its loading is not shown. The page says so.

**Agent runs:** 2 (142 of the session's 150).

**CI:** all five jobs green on the [pull request](https://github.com/ryantornberg/agent-ready-workspace/actions/runs/44002663956) and on [`main` after the merge](https://github.com/ryantornberg/agent-ready-workspace/actions/runs/44003119057). **Run live after the merge,** at `50f810f` in the main checkout: `selftest`, `check` and the unit tests pass, and the opt-in browser test passes again.
