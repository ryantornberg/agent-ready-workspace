# Red team review: docs/plans/m4-fail-closed-guards-review-loop-and-evals.md

A tenth fresh red team's attack on M4's draft hand-off plan, checking the claims its decisions rest on against the repository.

**In short:** holds with fixes, 8 findings. A review mark can be written while every blocking finding is still open. G4's new git-folder test would refuse ordinary writes in any folder holding a `config` entry.

The red team read the plan, the round 9 record, the red team review page and the sources the plan names, at the commit above, with a clean tree. It also read `.github/workflows/ci.yml`, `command_commits` and `command_check` in `wslib/runner.py`, `covered` and the hidden-test step in `evals/run.py`, `covered_files` in `parts/eval_record.py`, the header of `parts/git_folder_shell.py`, `parts/edit_ledger.py`'s docstring, the review orchestrator's steps 8, 9 and its closing paragraph, `docs/orchestration.md`'s limits, the README's Limits bullet on the parser, `src/README.md`, `outward-repos.json`, the two stored selection results and M3's "Known limits, for M4". It ran the before-shell hook on each row example F11 to F19 and F28, `python3 ws.py check`, the V8 `prove-by` grep, a Fisher exact computation of the two-line screen, and a count of entry types in three local Claude Code session transcripts. Nothing a guard judges was executed: no push, no `gh` write, and no agent, eval or selection run.

## Verdict

**Holds with fixes.** The core holds: one literal-word rule in the parser, grading files out of the recording's hash, staged eval budgets, and a review mark bound to dispatched sessions. But the mark's refusals reach only rows that already carry a disposition. So the cheapest path, one round and a mark with its findings still open, passes every gate the plan builds (finding 1). Round 9's fix to G4 widened the git-folder test so far that it would refuse ordinary work in many repositories (finding 2). Teach-back, as now written, cannot earn a mark whenever the grader asks a follow-up (finding 3). Each has a local fix. The rest are contradictions a builder would stop on.

| 2 | Round 9's fix makes G4's git-folder test refuse ordinary writes in any folder that holds an entry named `config` or `HEAD`. G4 now says a folder "counts as a git folder when it is named `.git`, or when it holds `HEAD` or `config` at hook time". Any command that names a path inside a git folder passes only for a program that only reads. A Rails application, and many Node projects, keep a `config/` folder at their root. So every write by `cp`, `mkdir`, `rm`, `npm`, `sed -i` or `tee` anywhere in such a pinned repository would be refused. So would a write in `~/.ssh`, which holds `config` on this machine. Git itself does not treat a folder holding `config` alone as a repository. The sentence that carries the rule is also garbled ("as a bare repository does, so a write of the other into it is refused whichever comes first, so ..."). Round 9 meant something narrower: refuse writing the second of the two files into a folder that holds the first. Fix: count a folder as a git folder by name, or by git's own test, which needs `HEAD`, `objects` and `refs`. Then refuse, separately, a write of a file named `config` into a folder that holds `HEAD`, and a write of `HEAD` into one that holds `config`. Criterion 11 gains a case: a write in a folder whose root holds `config/` passes. | Verified, by reading G4's last bullet and criterion 11. Verified, by `find`: this repository holds no file or folder named `config` or `HEAD` outside `.git`, so the sample would not show the fault and G2's measure over its eval commands would miss it. Verified, by a test of `~/.ssh/config`: the file exists. Inferred, from git's documented repository discovery: a folder is a git folder when it holds `HEAD`, `objects` and `refs`.
