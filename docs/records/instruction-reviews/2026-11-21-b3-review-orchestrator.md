# Instruction review: docs/playbooks/review-orchestrator.md

This records the instruction review of the new review orchestrator playbook, for its author and for agents who run a multi-dimension code review.

**In short:** 7 findings: 2 contradiction, 5 step. The routing table, the planned-machinery table and the rules table hold. The defects sit where this page meets others: what its dispatch hands the reviewer pages it names, what its record writes against what step 2 reads back, the definition of done's warning rule, the contract's worktree rule, and pull requests in pinned repositories.

## Findings

| # | Class | Where | Finding | Disposition |
|---|---|---|---|---|
| 1 | contradiction | Steps, step 4 (the mechanical pre-pass), against the definition of done | Step 4 counts "a new warning only in a file the range changes". The definition of done's list says "Compare warnings with the base branch and count only new ones", with no limit to changed files. A change that deprecates a method raises new warnings in its unchanged callers: the definition of done says the work is not done, while the pre-pass reports it clean and lets the run go on. The page does not label the narrowing as an exception. Verified: read step 4 and the definition of done's second row. Cause: pass-contradiction-skipped — the brief requires reading the definition of done in the contradiction pass, and the narrowing survived it. | fixed: step 4 now counts every new error and every new warning, as the definition of done does, and the stop and its rule row match. |
| 2 | contradiction | Steps, steps 3 and 4, against AGENTS.md "Facts a model cannot derive" | The contract says to work in a worktree of your own only when the lease refuses an edit. Step 4 always makes a second review worktree at the base, on your own branch as well, and step 3 makes one at your own tip when a tracked change exists. The labelled exception in review in a worktree's "Why a worktree, as an exception" gives one reason, a pull request's files at its exact commit, which covers neither use. This page labels no exception and gives no reason. Verified: read both steps, the contract's third fact and that section. Cause: pass-contradiction-skipped — the brief names "when a worktree is used" as a contradiction to watch, and these two uses carry no exception. | fixed: step 3 now labels each review worktree as an exception to the contract, pointing at review in a worktree, whose exception now covers any commit a review reads, its tip and base included. |
| 3 | step | The dispatch template, against the dimensions table | The template carries only the dimension, the folder, the range and the request. Architecture review's step 4 takes "the diff, the request, the plan and this page", and its big-picture pass reads the plan's "Settled decisions"; the template has no plan. Reuse checklist's reviewer step 2 takes "the author's line", and its default makes a missing line "a finding of its own"; the template never passes the line, so every reuse dimension reports that finding. Verified: read the template, architecture review's step 4 and big-picture step 3, and reuse checklist's reviewer step 2. Cause: brief-silent-on-dispatch-interface — the step pass checks each step's own inputs, but never asks that a dispatch carry every input the receiving page's steps name. | fixed: the dispatch template now carries the plan's path and the author's reuse line, each or none, and step 6 names both as inputs. |
| 4 | step | The dimensions table, the Test adequacy row, and the dispatch template | The row says the reviewer follows "Test first, including the red-green proof for a bug fix", but names no reviewer's steps. The template then tells the reviewer to "Follow the reviewer's steps of <page>". Test first has no reviewer's steps: its steps write tests and code, which the template's "Edit nothing" forbids. The page gives no default for what the reviewer checks. Verified: read test-first.md in full; it has Steps, the red-green proof, test guidance and Rules, none for a reviewer. Cause: brief-silent-on-dispatch-interface — the brief does not ask that a page named as a reviewer's steps actually has steps a read-only reviewer can run. | fixed: the Test adequacy row now names test first's red-green and good-test sections as what to check, not steps, and the template says Use <guide>. |
| 5 | step | Steps, step 2, against step 11 | Step 2 counts an earlier review complete "when it has no `Not complete:` line", and on a complete review of this tip it stops. On someone else's pull request, step 10's record goes only in the report, and the one thing posted is step 11's overview. The overview ends with `<!-- review: range ..., patch <id>, dimensions <list> -->` and never carries a `Not complete:` line. So a round with a failed dimension reads as complete next time, and step 2 stops without running it. Verified: read steps 2, 7, 10 and 11. Cause: brief-silent-on-write-read-match — the step pass checks each step alone, not that what one step writes holds what another step reads back. | fixed: step 11's marker now carries a not-complete list, and step 2 reads it, so a failed dimension is not read as complete. |
| 6 | step | Steps, step 10, against step 2 | Step 10 writes `Patch id: <id>`, and step 11's marker `patch <id>`, but no step computes it on a full or delta round, and neither says of which range. Step 2's rebase case compares it against `git diff BASE..TIP \| git patch-id --stable` over the whole branch. If a delta round records the patch id of its own `REVIEWED..TIP` range, the next rebase never matches. Verified: in a scratch clone, `git diff B..T \| git patch-id --stable` printed the id and a zero commit id, so the first field is right; step 10's input list names no patch id. Cause: brief-silent-on-write-read-match — the record's fields were not checked against the step that reads them. | fixed: step 10 now says the patch id is computed over the whole branch, BASE..TIP, on every round, and step 2 compares the same range. |
| 7 | step | Steps, steps 1, 2, 5 and 11 | Step 11 posts to a pull request in a pinned repository with `-R OWNER/REPO`, so the page covers one. But step 2's `gh pr view NUMBER --json body,reviews,comments`, step 5's `gh pr view NUMBER --json body`, step 1's `gh pr view NUMBER --json baseRefName` and `git merge-base origin/TARGET TIP`, and step 11's `gh pr view` and `gh api "repos/{owner}/{repo}/..."` carry no `-R` or `-C src/REPO`. Run from the main working copy, they read this repository's pull request of the same number. Verified: `gh api --help` says `{owner}` and `{repo}` come from the current directory's repository or `GH_REPO`; `gh pr view --help` shows `-R`. Cause: sample-cannot-exercise-pins — the step pass asks to run each command, but this sample has no pinned repository, so the pinned variants were never run. | fixed: step 1 now says a pull request in a pinned repository runs every git command with -C src/REPO, every gh command with -R, and names owner and repo in gh api paths. |
