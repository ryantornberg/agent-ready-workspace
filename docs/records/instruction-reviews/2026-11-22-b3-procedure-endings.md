# Instruction review: docs/procedure-endings.md

This records the instruction review of the new procedure endings page, for its author and for anyone writing a page that links it.

**In short:** 11 findings, 2 of them blocking: 3 contradiction, 4 step, 1 trigger, 1 enforcement, 1 placement, 1 eval-case. The blocking two: the question-log step commits another session's uncommitted rows, and no commit or push path covers a code change.

## Scope

In scope: the whole page, as a new reference page. Read in full: the page; the diffs of `docs/how-tos.md`, `docs/question-log.md` and `docs/playbooks/instruction-review.md`; and beside them `AGENTS.md`, `INDEX.md`, `workspace.json`, `docs/commits.md`, `docs/changing-the-machinery.md`, `docs/definition-of-done.md`, `docs/layout.md`, `docs/playbooks/fix-a-bug.md`, "Which writes need a yes" and "Steps" in `docs/playbooks/tracker-operations.md` and `docs/playbooks/git-host-operations.md`, decision 0005, and the plan's paragraph that names the page. Broke:

- Blocking. Finding 6's fix has the main working copy run `git pull --rebase origin main` when main moved, before the push and again after a not-a-fast-forward rejection. That command fails whenever a tracked file holds an uncommitted change. The page creates that state itself: finding 1's fix leaves your own row uncommitted in `docs/question-log.md`, and the contract says to leave other sessions' uncommitted changes in place. In a scratch repository, with main one commit ahead and one behind and an unstaged row in the log, the pull printed "error: cannot pull with rebase: You have unstaged changes" and exited 128, and `git push origin main` was then rejected as non-fast-forward. Verified. No repository or global `rebase.autoStash` is set, verified. The page gives no step for this failure, and the obvious recovery, `git stash` or `--autostash`, sweeps other sessions' changes, which "Leave other changes alone" forbids and decision 0005 lists as a cost ("stashes catching everyone's edits"). Inferred.
- Not blocking. Finding 1's fix left four unconditional statements that the new exception contradicts, none pointing to it: The order's step 3 ("the log included"), The commit's opening ("and the question-log row of step 2"), the question-log entry's third bullet ("still commits this entry"), and the rules row "commit the entry, before the report". An agent reading The commit alone stages the log with others' rows, as before the fix. Verified, by reading.
- Not blocking. Once one row is left uncommitted, every later session finds rows it did not add, so no session commits the log again, and the page names no one who does. The lingering tracked change also stops decision 0005's start-of-session fast-forward, which needs a main copy with no tracked change. Inferred.
- Not blocking. Finding 2's fix sends code to "the procedure that made it", while the page's last rule tells a procedure to link this page instead of restating its rules, and the instruction review counts a restatement as a finding. When fix a bug's step 5 is next edited and replaced by a link, each page will point to the other, and none will say where a code change is committed or pushed. Today step 5 still holds the rule, verified; the loop, inferred.
