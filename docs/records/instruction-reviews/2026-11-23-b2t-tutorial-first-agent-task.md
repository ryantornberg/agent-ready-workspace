# Instruction review: docs/tutorials/first-agent-task.md

This records the instruction review of slice B2t's new first-agent-task tutorial, for its author and for the newcomer who runs it.

**In short:** 6 findings: 2 contradiction, 2 step, 1 placement, 1 trigger. 2 are blocking: `python3` as written fails on a common Windows setup, and under Codex CLI on Windows the agent's edit in step 4 is refused.

## Scope

The page is new and uncommitted, so the whole page was in scope.

Read beside it: `AGENTS.md`, `CLAUDE.md`, `INDEX.md`, `README.md` ("Try it", "What is checked, and by what", "Limits"), `docs/layout.md` ("Page kinds", "The opening", "Tutorials"), `wslib/blocks.py`, `wslib/launch.sh`, `wslib/lease.py` (`tool_pid`), `tests/test_tutorials.py`, `.github/workflows/ci.yml`, `docs/procedure-endings.md`, `docs/question-log.md` (its kinds and "The kickoff prompt"), `docs/commits.md`, `docs/machine-self-check.md`, `docs/research-ladder.md`, decision 0005, `workspace.json` (the `review_trailer` entry), `.gitignore`, and `docs/tutorials/get-oriented.md`.

Ran, on macOS only: cloned the worktree's HEAD (18eccc5) into a scratch folder, copied both tutorials in, committed them there with `--no-verify` and a throwaway identity, and called `wslib.blocks.run_tutorial` on the page. It passed: the branch was made and deleted, the lookup printed the file and line, and `ws.py check` gave only the expected `eval_record` warning. Linux and Windows were not run. CI cannot run steps 2 to 4, which need an agent, so in a second scratch clone the person's side was simulated: on `practice-first-task`, one row added to the question log, staged by name and committed as `docs: log a practice question` with the hooks given by `-c core.hooksPath=.githooks`. The commit passed with no trailer; `git status --short` then printed nothing; `git show --stat HEAD` named one file with one line added; step 8's block returned to main and deleted the branch. No agent session was run.

## Findings

| # | Class | Where | Finding | Disposition |
|---|---|---|---|---|
| 1 | step | "Before you start", and the blocks of steps 3 and 6 | Blocking. The page says the reader's blocks run as written on Windows, in Git for Windows' bash, and that CI runs them there. But the Python installer for Windows gives no `python3`, as `wslib/blocks.py` says beside `LAUNCHER` and machine self-check step 1 says; what is left is often the Windows Store stand-in, which the launcher skips. In CI, `run_tutorial` defines `python3` as a function that calls `wslib/launch.sh`, so CI cannot see the command fail. A Windows reader following the page runs a command that fails at step 3. Fix: as for get oriented, tell the Windows reader to use `bash wslib/launch.sh` in place of `python3`, and say that CI runs `python3` through the launcher. Verified by reading `blocks.py`, `launch.sh` and machine self-check step 1; the failure on a Windows machine is inferred, not run. | fixed: the reader works in a clone set up as get oriented's step 1 says, which sends python3 through the launcher. |
| 2 | step | "Before you start" (Codex CLI as a supported tool), with "4. Make a one-row change" | Blocking. An edit to a tracked file in the main working copy needs a lease, and a lease needs the agent tool's process id. For Codex CLI on Windows none is read: `tool_pid` in `wslib/lease.py` returns `None` when `os.name` is `nt`, and decision 0005 says "a Codex edit that needs a lease is refused there". So on Windows under Codex, the agent's edit to `docs/question-log.md` is refused, step 4 cannot be done as written, and step 5's expected output never appears. The page names the case for a refused commit only; an agent that works around a refused edit, such as by writing through the shell, which takes no lease, skips a guard. Fix: say that on Windows, Codex CLI cannot do step 4 in the main copy, and name the route: Claude Code, or a worktree of the agent's own. Verified by reading `lease.py` and decision 0005 ("What needs a lease", the identity table, "Limits"); the refusal on a Windows machine is inferred, not run. | fixed: the page names Codex CLI on Linux or macOS only, and Claude Code on Windows, citing decision 0005. |
| 3 | contradiction | "Before you start", with "6. Run the checks yourself" | Not blocking. The page asks for "the same clone, with its hooks wired", then suggests "a fresh clone in a scratch folder". `core.hooksPath` is local to a clone: a fresh clone has none, as the scratch clone showed. A reader who takes the suggestion runs step 4 with no commit hooks, so step 6's "The commit hook already ran these" is false, and the post-commit hook that closes the edit ledger's paths does not run. Fix: either drop the fresh-clone suggestion, or add `git config core.hooksPath .githooks` to step 1's block. Verified: `git config --get core.hooksPath` printed nothing in a fresh scratch clone. | fixed: the fresh clone is set up as get oriented's step 1 says, which wires the hooks. |
| 4 | contradiction | "2. Start the agent", the Codex CLI trust sentence | Not blocking. The page says Codex asks the reader to trust the project before its hooks run, and to say yes. The README's "Limits" says Codex runs a project's hooks only after you trust the project and review its hooks with `/hooks`, and machine self-check step 4 asks for both. A reader who only trusts the project runs steps 3 and 4 with no hook, so no guard watches the agent's edit or shell calls; only the commit check runs. The page also says this is "as the machine self-check says", but the self-check asks the question and gives no instruction to say yes. Fix: add the `/hooks` review, and link the README's Codex limits. Verified by reading the three pages. | fixed: step 2 says to trust the project and review its hooks with `/hooks`. |
| 5 | placement | "4. Make a one-row change", the paragraph "Watch for three things" | Not blocking. The paragraph restates rules that [procedure endings](../../procedure-endings.md) states, instead of linking them: staging by name ("The commit"), no `Instructions-review:` trailer because the log is a record ("The question-log entry"), and what to do when a commit is refused. The last one has drifted: procedure endings says to read the refusal, fix what it names and commit again, then leave the files uncommitted and name them in the report; the page says "read the refusal and say so, not work around it". Step 3's sentence on marking claims verified or inferred restates "The report" too. The instruction review counts a restated rule as a finding. Fix: keep the three things to watch, and link each to its section. Verified by reading both pages. | fixed: step 4 links procedure endings' "The commit" for what to watch. |
| 6 | trigger | The purpose sentence | Not blocking. Layout's "The opening" asks the purpose sentence to say what the page is for and who reads it. This one names the task and its parts but no reader, and the **In short** line names none either. Verified by reading the opening against `docs/layout.md`. | fixed: the purpose line names the newcomer. |

## Checked with no finding

- step, beyond findings 1 and 2: the reader's blocks ran green on macOS in a fresh clone of the commit; in the simulation the commit of step 4 passed the hooks with a `docs:` subject and no trailer, as the page predicts, since `workspace.json` lists `docs/question-log.md` under `review_trailer`'s `except`; step 5's three expected outputs held; step 8's `git checkout -q -` returned to the branch held before step 1 and `git branch -D` removed the practice commit; `could not find` is one of the question log's kinds; the links to `#3-run-the-checks` and `#the-kickoff-prompt` resolve (the `links` check passed); `.claude/settings.local.json`, which Claude Code may write, is ignored, so it does not break step 5's empty `git status`.
- contradiction, beyond findings 3 and 4: step 3's "good answer" goes from the alias to `symbols.py`, which the research ladder allows ("it gave you something new, such as a code name from an alias: then … pick again"), so it is not a stacked lookup. Step 4's prompt asks for a commit on the practice branch and no push, against procedure endings' default of a pages-only commit on main and a push; the person's own instruction names both, so the agent has no conflict to settle. Step 7's "on main, not on this branch" matches procedure endings' "Where the commit goes".
- enforcement: the page states one enforcement, that CI runs the reader's blocks on three systems. `tests/test_tutorials.py` and `.github/workflows/ci.yml` hold it, except for how `python3` runs on Windows (finding 1). The agent's side has no enforcement and the page claims none; it asks the reader to watch for it.
- eval-case: the behavior the page expects of the agent, staging by name, a conventional subject, claims marked verified or inferred, and the alias-then-symbol route, is the contract's and the research ladder's, not new behavior; a tutorial carries no proof state.
