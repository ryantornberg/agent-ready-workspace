# Instruction review: docs/playbooks/feedback-walkthrough.md

This records the instruction review of the new feedback walk-through playbook, for its author and for agents that take an author through review comments.

**In short:** 5 findings: 1 contradiction, 3 step, 1 trigger. A fix to a guidance page has no path through steps 5 to 7. The route for a single comment skips the size gate and the author's yes. Step 1 has no failure path for its fetch. Step 7's review loop has no exit the author can reach by skipping. No step names the repository for a pull request in a pinned repository.

## Scope

In scope: the whole page. Read beside it: `AGENTS.md`, `CLAUDE.md`, `INDEX.md`, `docs/definition-of-done.md`, `docs/orchestration.md` (with its batch 3 diff), `docs/layout.md`, `docs/glossary.md`, every page it links to (`docs/playbooks/fix-a-bug.md`, `docs/playbooks/review-orchestrator.md`, `docs/review-in-a-worktree.md`, `docs/size-the-work.md`, `docs/playbooks/test-first.md`, `docs/safe-refactor.md`), the batch 3 diffs of `docs/changing-the-machinery.md` and `docs/playbooks/README.md`, `docs/code-review.md`, `docs/playbooks/instruction-review.md`, decision 0005, and the `review_trailer` entry in `workspace.json`. ## Findings

| # | Class | Where | Finding | Disposition |
|---|---|---|---|---|
| 1 | contradiction | Steps, steps 5 to 7 | A comment can ask for a change to a guidance page, which the `review_trailer` entry in `workspace.json` lists as every page under `docs/`, `AGENTS.md`, `INDEX.md` and the README. Step 5 routes a fix only to fix a bug or safe refactor. Step 6's commit is refused by the commit-msg hook without an `Instructions-review:` trailer, and the page gives no step for that refusal. Step 7 sends the round to the review orchestrator, whose "When it runs" table says that for a change made only of guidance pages "this playbook does not run". So a round of guidance fixes can neither commit nor be reviewed as the page says. Verified: read `workspace.json`'s `review_trailer` entry, steps 5 to 7, and the orchestrator's table. Cause: brief-silent-on-guidance-changes — the brief tells builders how their own pages are reviewed, not that a playbook which edits and commits must route guidance pages to the instruction review. | fixed: step 5 sends a change to a guidance page through its instruction review with the trailer before step 6 commits it, and step 7 leaves guidance-only commits out of the orchestrator's range. |
| 2 | trigger | When to use it, the table's second row | "The author names one comment and asks only for its fix" goes to fix a bug, "since that is one small change". One comment can ask for a change that fails the size gate, which `AGENTS.md` "How work flows" and this page's own step 5 apply before fix a bug. Fix a bug's step 5 also commits without asking and opens a draft pull request, though the branch already has one, while this page's step 6 says a commit needs the author's yes because "the author is present and owns the branch's history". The row fires fix a bug where its rules do not fit. Verified: read the row, steps 5 and 6, fix a bug's steps and `AGENTS.md`. Cause: contradiction-pass-skipped — the brief names "where work goes (fix a bug versus the size gate's ladder)" as a trap to check. | fixed: the one-comment row now routes to this page with that comment as the only queue item, so the size gate and the ask-before-commit rule both apply. |
| 3 | step | Steps, step 1 | Step 1 runs `git fetch origin HEADREF` and compares with `origin/HEADREF`, but says nothing when the fetch fails. A pull request from a fork has its head branch on the fork, not on `origin`, so the fetch fails there, and the comparison has no ref. The step's stop list covers the state, the branch and the count, not a failed fetch, so this branch does not end in the report. Verified: read step 1 and the "Stop when" line. That the fetch fails for a fork is inferred. Cause: step-pass-skipped — the step pass requires every failure path, such as a refused check, to end in a report. | fixed: step 1 now stops and reports the error when the fetch fails, naming a pull request from a fork as the case. |
| 4 | step | Steps, step 7 | Step 7's input is "the commits this round made", and it loops to step 3 until "the review finds nothing". "This round" is not defined; step 5 uses it for the whole walk-through. Read that way, when the author skips or declines every finding of a review, the next pass through step 7 still has commits, sends the same commits to the orchestrator again, and gets the same findings back as new items. The page gives no exit for that case, unlike `docs/orchestration.md`'s limits, where an attended loop ends on a round that only finishes earlier work. Verified: read steps 5 and 7 and the limits. The repeated findings are inferred from the orchestrator's step 2, not run. Cause: step-pass-skipped — the step pass asks that each step say when to stop and send the reader back only on a condition it can detect. | fixed: step 7's input is the commits since the last pass, or since step 1's head commit, and a pass with no new commits goes to step 8, so skipped or declined findings end the loop. |
| 5 | step | Steps, steps 1, 2 and 8; Posting | The Posting section treats a pull request in a repository pinned under `src/` as a case the page covers. No step names the repository as an input or gives the `-R OWNER/REPO` or `git -C src/REPO` form, as review in a worktree's step 1 does. Run from the main working copy, every `gh` and `git` command in steps 1, 2 and 8, including the `{owner}/{repo}` placeholders, reads this workspace's repository instead. Verified: read the steps, the Posting section and review in a worktree's steps 1 and 2. Cause: step-pass-skipped — the step pass asks that each step name its input and where it comes from. | fixed: step 1 takes the repository as an input, defaulting to this one, and a paragraph under When to use it gives the -C src/REPO, -R OWNER/REPO and OWNER/REPO forms for a pinned repository. |
