## Findings

| # | Class | Where | Finding | Disposition |
|---|---|---|---|---|
| 1 | enforcement | The rules table, the `secrets_shell` row | Blocking. The row now says "every shell guard judges that program as if it ran by its own name". That is false for the guards that read the variables a command sets. `with-secrets` accepts any variable name and puts the file's value in the child's environment, but the parser reads the child with none of those variables set, and the runner works out a gh call's repository from the session's environment. So `GH_REPO=other/theirs gh pr create ...` is refused, and `python3 ws.py with-secrets GH_REPO -- gh pr create ...` passes, judged against this repository, while gh writes to the repository the file names; `GH_HOST` alike. Before slice Z, git and gh under `with-secrets` were refused outright, so the route is new. The row's Enforced-by column names only `secrets_shell` and `ws.py with-secrets`, and the `secrets_shell` limit under "Limits" does not name the gap. An agent relying on the row can write to a repository outside the list with no yes. The agent settings record, 2026-11-24-z-agent-settings.md, finding 1, holds the full evidence and the fix's two shapes. Verified: `outward_write.decide` refuses the `GH_REPO=` line and allows the `with-secrets GH_REPO` and `with-secrets GH_HOST` lines, with targets from `shellfacts.targets`; `wslib/secrets.py`, `split`, accepts any name. That gh honours `GH_REPO` from its environment is inferred. | fixed in code: each NAME `with-secrets` hands in now reaches the child as a value the line does not show, so `GH_REPO` handed in leaves the gh target unresolved and `outward_write` refuses it (a parser test and an `outward_write` case); the page now says so |
| 2 | contradiction | Limits, the bullet "`secrets_shell` reads command lines, and `with-secrets` narrows where a value goes without sealing it" | Not blocking.
