Broke:

- Blocking. The fix made ws.py's own launcher forms stop counting as the wrapper. Since slice Z, `secrets_shell` no longer refuses git, gh or a write under `with-secrets`, so nothing judges the child of these forms. `sh wslib/launch.sh ws.py with-secrets T -- git push --force origin main`, `wslib/launch.sh ws.py with-secrets T -- rm .git/config`, `bash wslib/launch.sh ws.py with-secrets T -- gh pr create --fill -R them/theirs`, `wslib/launch.sh ws.py with-secrets T -- gh pr merge 1 --admin` and `python3 wslib/start.py . ws.py with-secrets T -- git push --force origin main` pass every before-shell hook. So does `python3 --check-hash-based-pycs default ws.py with-secrets ...`, since that option's value is taken for the script. fca7d9b refused each through the guard on the child, and d2aa593 through `secrets_shell`. `wslib/start.py` runs these forms as `ws.py with-secrets`. The workspace's git hooks and CI call ws.py as `sh wslib/launch.sh ws.py ...`, so an agent has a model to copy. `with-secrets` itself still refuses a shell, `env` or `printenv` as its child, so a leak through a shell stays closed; it does not refuse git, gh or `rm`. The amendment's own condition is literally true of these forms, but its next sentence, that the push, outward-write and git folder guards refuse git, gh and writes under the wrapper, is not. `_with_secrets_child`'s docstring still says ws.py is found wherever it stands and that the launcher counts. Verified: the hooks on the three trees, `wslib/start.py`, and `secrets.refusal`, which gives None for `git`, `gh` and `rm`. Inferred: that an agent reaches for the launcher form. The README's limit that "a script" can write anywhere may be read to cover it; marked blocking because it reopens what both earlier trees refused.
- Blocking. The amendment's new sentence, that a `GH_REPO` or `GIT_CONFIG_*` name handed in leaves the target unresolved and the guard refuses it, is false for a NAME the line gives by a variable or substitution. The parser takes the word's text as the name. So `N=GH_REPO; python3 ws.py with-secrets "$N" -- gh pr create --fill` and `python3 ws.py with-secrets $(echo GH_REPO) -- gh pr create --fill` pass every hook, judged against this repository, and `python3 ws.py with-secrets "$N" -- git push origin HEAD:refs/heads/probe-x` passes too. The literal forms are refused. The line form `env "$N=x" gh pr create --fill` is refused, as a program that is a variable. Verified: the hooks, and `env_dynamic` of `['$N']` in the parse. Inferred: that ws.py then hands gh the file's `GH_REPO`, from `secrets.split`, which takes the expanded word.
