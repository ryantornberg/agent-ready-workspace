## Findings

| # | Class | Where | Finding | Disposition |
|---|---|---|---|---|
| 1 | enforcement | Secrets in the shell, the bullet "Every shell guard judges the program it starts" | Blocking. The bullet says a push meets the push guards and a gh write the outward-write guard "as if run by its own name". That is false for every guard that reads the variables a command sets. `with-secrets` puts the named values in the child's environment, and it accepts any variable name, so the file can supply `GH_REPO`, `GH_HOST`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, `HOME` or `GIT_DIR`. The parser reads the wrapper's child with none of those set, and the runner works out a gh call's repository from the session's environment, not the file. So `GH_REPO=other/theirs gh pr create ...` is refused, while `python3 ws.py with-secrets GH_REPO -- gh pr create ...` passes both `secrets_shell` and `outward_write`, judged against this repository, and gh then writes to the repository the file names. The same holds for `GH_HOST`, and for a push whose remote URL a `GIT_CONFIG_*` value in the file rewrites. Before slice Z the hook refused git and gh under `with-secrets` outright, so this route is new with the change. An agent following the bullet can write to a repository outside the list without anyone's yes; the page itself says an agent can write the file by a redirection ("A write to a secrets file by a redirection passes"). Neither this page's Limits nor the README's limits name the gap. A fix either refuses names that steer git or gh (the config, SSH, `GH_REPO`, `GH_HOST` and `GIT_DIR` variables), or has the parser report each named variable as set with a value it cannot know, which the guards already refuse (`GH_REPO="$X" gh pr create` is refused as a variable repository). Verified: `shell.analyze` gives the wrapped call `env {}` and `gh.repo None`; `shellfacts.targets` gives this repository as the destination; `outward_write.decide` refuses the `GH_REPO=` line and allows the `with-secrets GH_REPO` and `with-secrets GH_HOST` lines; `wslib/secrets.py`, `split`, accepts any name matching `NAME`. For the push, `shell.analyze` reports no config write for `with-secrets GIT_CONFIG_PARAMETERS -- git push origin HEAD` where the same value on the line is reported and refused, and `targets` names only this repository; that `outward_write` then allows it is inferred, since this review did not build the runner's `destinations` fact. That gh honours `GH_REPO` from its environment is inferred from the runner's own docstring ("-R or --repo, then GH_REPO, then the set-default value"). | fixed in code: each NAME `with-secrets` hands in now reaches the child as a value the line does not show, so `GH_REPO` handed in leaves the gh target unresolved and `outward_write` refuses it (a parser test and an `outward_write` case); the page now says so |
