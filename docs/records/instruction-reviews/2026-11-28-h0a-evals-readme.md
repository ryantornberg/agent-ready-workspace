Broke:

1. Not blocking. The last sentence of "The gate", "After a change to `grade.py` itself, `eval_record` refuses it unless the runs were recorded since the base", reads as if only a new recording gets past. "Recorded since" means only that a transcript's content differs from the base's, so a hand edit counts. Verified: a `grade.py` edit that passes one failing guided run, the record's grades edited to match, and one action appended to each transcript of the three gated records. Then `ws.py check --phase ci --changed-from <base>` exited 0, `grade.py --recorded --base <base>` found no difference, the stamp wrote the three records, and fix-a-bug's guided arm went from 14 to 15 passing. The paragraph already says the gate cannot stop a transcript written by hand; the sentence should say that this is how that limit reaches `grade.py`.

Missed:

1. Blocking. "Record every case again, then stamp" ends in a failing command. After the three gated cases are recorded again, the stamp writes their records but refuses the twelve one-time records, whose runs the base holds, and exits 1. Each refusal says "record case big-report again, then stamp" (or fix-a-bug, nightly-job), naming a case the agent has just recorded. Verified: after a `grade.py` edit and new content in every transcript of the three gated records, the stamp printed twelve "not stamped" lines and "stamped the grader hash into 3 record(s)", exit 1, while `ws.py check --phase ci` exited 0. An agent following the page records the named case again, 45 runs, and gets the same exit. H0b's change to `grade.py`'s search (plan item 10) is the first to meet it (inferred). Fix: report the one-time records as left, not refused, since the gate never reads them, or name `--one-time <arm>` in the message; and say on the page what the stamp does with them.
