## Findings

| # | Class | Where | Finding | Disposition |
|---|---|---|---|---|
| 1 | step | "The gate", the first and second paragraphs | Blocking. The page names recording the case again as the way out twice: "Edit any of those files and the commit fails until every case has been run again", and, for a grade that differs, "the case must be recorded again". At H0a, `run.py` writes no grader hash: `build_record` writes `guidance_sha256` and no `grader_sha256` or `grader_covers` (verified: `grep grader evals/run.py` finds neither key). `eval_record` fails such a record: with the fields removed from `evals/runs/fix-a-bug/record.json`, `python3 ws.py check` gave "its record of case fix-a-bug holds no grader hash; run python3 evals/grade.py --recorded --stamp" (verified). So an agent that records the case and commits, as the page says, has the commit refused. The page's own sentence "as it fails a record with no grader hash" does not say that every new recording is such a record until H0b. The step after a recording, the stamp, is missing. | fixed: the first paragraph and "Run it yourself" name the stamp after any recording, before the commit |
| 2 | contradiction | "The gate", the second and third paragraphs | Blocking. "When a grade differs, it writes nothing, and the case must be recorded again" does not hold for a change to `grade.py` itself. A new recording is graded by this `grade.py`; the stamp and CI then re-grade it with the base commit's copy too, which still applies the old rule, so every run the rule change touches differs again. Verified by simulation: after a `grade.py` edit that changed one grader and a re-grade of the five fix-a-bug records by the new copy, `python3 evals/grade.py --recorded` found no difference in those records by this `grade.py` and 194 by the base commit's, and `--stamp` printed "nothing stamped". So a grading rule change that alters a grade can pass neither the stamp nor CI's re-grade by recording again, while the base holds the old copy. For a hook or the parser, both copies load this tree's file, so recording again does clear it (inferred from `base_copy`, which sets the module's `__file__` to this tree). The page says neither. | fixed in code: the base commit's `grade.py` now judges only the runs the base holds, and a run recorded since the base is judged by this `grade.py` alone (`evals/grade.py` `judged_by_base`; test `test_a_grade_py_change_that_alters_a_stored_grade_fails_and_passes_once_the_case_is_recorded_again`); the page says so |
| 3 | contradiction | "The gate", the second paragraph, against `AGENTS.md`'s rules table | Blocking. The page tells an agent that a change to grading files alone "needs no new run. The plan accepts this until H0b rewrites the contract's eval rule (triage item R2-11 and the H0b section; verified), but the page does not label the exception. | fixed: the page labels the exception until M4's slice H0b rewrites the contract's eval rule; the contract edit is queued for H0b |
